# Live test — download + frames + pruning, end to end

**Date:** 2026-11-09 · **Where:** the draw-yt development VM (datacenter IP,
the same network where YouTube downloads were measured as bot-blocked on
2026-11-05) · **Tool:** yt-dlp 2026.10.26, ffmpeg, the `drawyt` CLI in this repo.

## Question

Can this machine, running this code, actually download a YouTube video and
turn it into pruned frames — not in theory, today?

## Routes tried (one attempt each)

| Route | Result |
|---|---|
| default web client | ❌ `Sign in to confirm you're not a bot` |
| `player_client=android` + `--no-check-certificate` + `--js-runtimes node` | ✅ downloads |

The 2026-11-05 conclusion ("pixel download is blocked from this VM") held
only for the default client. The android route works from the same VM, same IP.

**Known limitation, measured:** in this session the android route only
delivers format 18 (360p) — YouTube's SABR-only experiment skips the other
android HTTPS formats. Fine for presence/pruning work; not the ceiling on a
residential connection, where the default route (tried first) delivers
video-only streams up to the configured cap.

## Pipeline on the downloaded Short (`sVTAtgzPGhA`)

```
extract @2 fps   -> 30 frames
prune (level 0)  ->  9 kept · dropped: 18 near-duplicate, 3 blurred
coreset (k-center, budget 8) -> 8 selected, manifest written
```

   prune, combined receipt — for the "give me this video's frames" use case.
